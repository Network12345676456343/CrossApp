# Лабораторна робота № 5
## Сервісний шар: інтерфейси, два сховища, ручний DI

### Мета роботи

Мета лабораторної роботи — реалізувати сервісний шар для роботи з видачами книг, забезпечити незалежність бізнес-логіки від способу зберігання даних, створити два взаємозамінні сховища та реалізувати ручне впровадження залежностей (Manual Dependency Injection) без використання сторонніх DI-контейнерів.

## 1. Опис виконаної роботи

Під час виконання лабораторної роботи було створено абстракцію сховища `ILoanStore`, яка визначає основні операції для роботи з видачами книг. Реалізовано два сховища: `InMemoryLoanStore` для зберігання даних в оперативній пам'яті та `FileLoanStore` для збереження даних у JSON-файлі.

Також створено сервіс `LendingService`, який працює через інтерфейс сховища, а вибір конкретної реалізації виконується в точці композиції застосунку (Composition Root). Це дозволяє змінювати спосіб зберігання даних без необхідності змінювати бізнес-логіку сервісу.

## 2. Контракт сховища, сервіс та Composition Root

### 2.1. Інтерфейс ILoanStore

У файлі `src/Core/Abstractions/ILoanStore.cs` визначено інтерфейс `ILoanStore`, який містить методи для виконання основних операцій зі сховищем видач книг.

Інтерфейс передбачає такі методи:

- `List()` — отримання списку всіх видач.
- `GetById(string id)` — пошук видачі за ідентифікатором.
- `Add(Loan loan)` — додавання нової видачі з перевіркою унікальності ідентифікатора.
- `Update(Loan loan)` — оновлення наявного запису.
- `Remove(string id)` — видалення запису за ідентифікатором.
- `Find(Func<Loan, bool> predicate)` — пошук видач за заданою умовою.

Для повернення колекцій використовується тип `IReadOnlyList<Loan>`, що забезпечує доступ до результатів без надання зовнішньому коду прямого доступу до внутрішньої колекції для її зміни.

Інтерфейс не залежить від конкретного способу зберігання даних, тому його можуть реалізовувати різні класи сховищ.

### 2.2. Сервіс LendingService

У файлі `src/Core/Services/LendingService.cs` реалізовано сервіс `LendingService`, який відповідає за виконання операцій із видачами книг.

Сервіс отримує залежність від `ILoanStore` через конструктор. Такий підхід називається впровадженням залежностей через конструктор (Constructor Injection).

Завдяки цьому сервіс не залежить безпосередньо від `InMemoryLoanStore` або `FileLoanStore`, а працює через спільний контракт.

Основні завдання сервісного шару:

- виконання операцій із видачами книг;
- отримання та пошук записів;
- перевірка наявності видачі перед виконанням операції;
- обробка ситуацій, коли потрібний запис не знайдено;
- взаємодія зі сховищем через інтерфейс.

### 2.3. Composition Root

У файлі `src/Cli/Program.cs` реалізовано точку композиції застосунку (Composition Root), у якій створюються необхідні об'єкти та визначається спосіб зберігання даних.

Для вибору файлового сховища використовується аргумент командного рядка `--file`.

Якщо аргумент `--file` передано, створюється екземпляр `FileLoanStore`. Якщо аргумент відсутній, використовується `InMemoryLoanStore` з початковими даними `SampleData.Loans()`.

Після вибору сховища створюється екземпляр `LendingService`, якому передається обрана реалізація інтерфейсу `ILoanStore`.

Такий підхід демонструє ручне впровадження залежностей (Manual DI) без використання сторонніх контейнерів.

## 3. Реалізація сховищ

### 3.1. InMemoryLoanStore

`InMemoryLoanStore` забезпечує зберігання видач книг в оперативній пам'яті.

Особливості реалізації:

- дані зберігаються лише під час роботи застосунку;
- після завершення процесу зміни не зберігаються;
- під час нового запуску завантажуються початкові дані, якщо вони передані в конструктор;
- сховище реалізує інтерфейс `ILoanStore`.

Ця реалізація підходить для тестування, демонстрації роботи сервісу та сценаріїв, у яких не потрібне постійне зберігання даних.

### 3.2. FileLoanStore

`FileLoanStore` забезпечує збереження видач книг у JSON-файлі.

Для серіалізації та десеріалізації використовуються об'єкти `LoanDto`, які дають змогу передавати дані між доменною моделлю та форматом зберігання.

Файл даних розміщується за шляхом, сформованим відносно каталогу застосунку:

`data/catalog.json`

Основні можливості файлового сховища:

- завантаження даних із JSON-файлу;
- збереження змін у файл;
- додавання нових записів;
- оновлення та видалення наявних записів;
- пошук записів за ідентифікатором або заданою умовою.

Файлове сховище дає змогу зберігати дані між запусками застосунку за умови, що всі операції запису реалізовані з відповідним оновленням файлу.

## 4. Сценарії запуску та перевірки

### 4.1. Запуск у режимі In-Memory

Для запуску застосунку з використанням сховища в оперативній пам'яті виконується команда:

```powershell
dotnet run --project src/Cli
```

У цьому режимі використовується `InMemoryLoanStore`.

Дані зберігаються лише в оперативній пам'яті. Після завершення роботи застосунку зміни втрачаються, а під час наступного запуску завантажуються початкові дані.

### 4.2. Запуск у файловому режимі

Для запуску застосунку з файловим сховищем виконується команда:

```powershell
dotnet run --project src/Cli -- --file
```

У цьому режимі використовується `FileLoanStore`.

Дані зберігаються у файлі `catalog.json`, що дає змогу відновити їх під час наступного запуску застосунку.

Для перегляду вмісту файлу можна використати команду:

```powershell
Get-Content "src\Cli\bin\Debug\net10.0\data\catalog.json"
```

Шлях відповідає наведеній конфігурації та типовому каталогу збірки Debug. Фактичне розташування файлу залежить від значення `AppContext.BaseDirectory` і способу запуску застосунку.

### 4.3. Перевірка обробки помилок

Для перевірки обробки помилкових ситуацій передбачено спробу виконати операцію повернення для неіснуючої видачі.

Приклад виклику:

```csharp
try
{
    service.ReturnCopy("UNKNOWN-ID");
}
catch (InvalidOperationException ex)
{
    Console.WriteLine(
        $"[Очікувана помилка перехоплена]: {ex.Message}");
}
```

Якщо запис із таким ідентифікатором відсутній, сервіс повідомляє про помилку, а виняток перехоплюється блоком `catch`.

Приклад очікуваного повідомлення:

```text
[Очікувана помилка перехоплена]: Позичку з Id='UNKNOWN-ID' не знайдено.
```

Ця перевірка демонструє обробку ситуації, коли операцію неможливо виконати через відсутність потрібного запису.

## 5. Додаткові завдання

### 5.1. Декоратор CachingLoanStore

Декоратор `CachingLoanStore` може використовуватися для додавання кешування до наявного сховища без зміни його основної реалізації.

Він реалізує інтерфейс `ILoanStore`, отримує базове сховище через конструктор і зберігає результати операцій у кеші.

Такий підхід дає змогу розширювати функціональність сховища без зміни клієнтського коду. Водночас під час реалізації необхідно забезпечити узгодженість кешу після додавання, оновлення та видалення записів.

### 5.2. Пошук за предикатом

Метод `Find(Func<Loan, bool> predicate)` дає змогу виконувати пошук видач за довільною умовою.

Наприклад, за допомогою цього методу можна отримати всі активні видачі, перевіряючи значення `LoanStatus.Active`.

Використання предиката робить інтерфейс сховища гнучкішим, оскільки дозволяє задавати різні умови пошуку без створення окремого методу для кожного випадку.

### 5.3. Фабрика StoreFactory

Фабрика `StoreFactory` може використовуватися для винесення логіки вибору та створення сховища з файлу `Program.cs`.

Вона дає змогу централізувати конфігурацію сховищ і підтримувати додаткові параметри запуску, наприклад `--file` та `--cache`.

У результаті файл `Program.cs` стає простішим, а логіка створення залежностей відокремлюється від запуску основного сценарію застосунку.

## 6. Висновки

Під час виконання лабораторної роботи було реалізовано сервісний шар для роботи з видачами книг і забезпечено його незалежність від конкретного способу зберігання даних.

Було визначено інтерфейс `ILoanStore`, створено реалізації `InMemoryLoanStore` та `FileLoanStore`, а також організовано передавання залежностей через конструктор сервісу `LendingService`.

Реалізований підхід демонструє принципи абстракції, слабкого зв'язування компонентів і впровадження залежностей. Використання двох сховищ дає змогу змінювати спосіб зберігання даних без необхідності переписувати бізнес-логіку сервісу.

Також розглянуто можливості розширення системи за допомогою кешування, пошуку за предикатами та фабрики для створення сховищ.

У результаті роботи було закріплено практичні навички проєктування сервісного шару, роботи з інтерфейсами та організації залежностей у застосунках на C# і .NET.
