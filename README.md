# Лабораторна робота № 6. Доменні події, делегати Action/Func, лямбда-вирази

## 1. Мета роботи

Реалізувати механізм сповіщення зовнішнього коду про зміни стану без залежності доменного шару від способу оброблення цих сповіщень: оголосити подію в Core, організувати підписку за допомогою лямбда-виразу в Cli та не використовувати Console.WriteLine у доменній логіці.

---

## 2. Архітектура та структура проєкту

- **`src/Core/Events/LoanChangeKind.cs`** — перелік типів доменних подій: `Issued`, `Returned`, `Cancelled`.
- **`src/Core/Events/LoanChangedEventArgs.cs`** — клас аргументів події, успадкований від `EventArgs`, який передає `LoanId`, `BookCopyId`, `ReaderId`, `Kind`, `DueUtc` та мітку часу `At`.
- **`src/Core/Services/LendingService.cs`** — сервіс, який оголошує подію `event EventHandler<LoanChangedEventArgs>? Changed`, містить приватний метод `OnChanged` із безпечним викликом `?.Invoke`, а також метод фільтрації `FindAll(Func<Loan, bool> predicate)`.
- **`src/Cli/Program.cs`** — точка композиції залежностей (Composition Root), у якій організовано двох підписників: локальний метод для логування у файл і консоль та лямбда-лічильник із замиканням. Також реалізовано демонстрацію відписки (`-=`) і сценарію відмови.
- **`logs/app.log`** — файл журналу подій, який створюється та заповнюється клієнтським кодом.

---

## 3. Демонстрація виконання

1. **Підписка та виклики.** Перший підписник форматує повідомлення та дописує його до `logs/app.log`, а другий підписник збільшує лічильник подій за допомогою замикання над локальною змінною.

2. **Керована відписка (`-=`).** Після відписки локального методу операції продовжують виконуватися, але повідомлення більше не виводяться в консоль і не записуються до файлу. Лямбда-лічильник продовжує фіксувати події.

3. **Сценарій відмови.** У разі порушення бізнес-правила, наприклад спроби повернути неіснуючу позичку, генерується виняток `InvalidOperationException`. Оскільки стан не змінився, подія не викликається, а лог-файл і лічильник залишаються незмінними.

4. **Використання `Func`.** Фільтрацію активних позичок реалізовано за допомогою делегата `Func<Loan, bool>`, який приймає об'єкт `Loan` і повертає логічне значення, що визначає, чи відповідає позичка заданій умові.

5. **Ізоляція доменного шару.** У просторі імен `Core` не використовуються виклики `System.Console` і прямі операції файлової системи для логування. Відображення та збереження повідомлень виконує клієнтський шар `Cli`.

---

## 4. Сценарій запуску в терміналі

Усі команди необхідно виконувати послідовно з кореневої директорії проєкту `C:\dev\CrossApp`.

### 4.1. Збірка проєкту

Виконати команду в PowerShell:

```powershell
dotnet build
```

**Очікуваний результат:** збірка завершується успішно без помилок.

```text
Build succeeded.
    0 Warning(s)
    0 Error(s)
```

### 4.2. Запуск програми у режимі In-Memory

Виконати команду:

```powershell
dotnet run --project src/Cli
```

**Що необхідно продемонструвати викладачу:**

**Крок 1. Робота двох підписників.**

- Спрацьовують обидва підписники.
- У консоль виводяться два повідомлення `[ПОДІЯ]` бірюзовим кольором.
- Лічильник показує `Подій отримано: 2`.

**Крок 2. Відписка від події.**

- Виконується відписка локального методу за допомогою `service.Changed -= OnLoanChanged`.
- Наступна операція виконується без повідомлення `[ПОДІЯ]` у консолі та без запису до лог-файлу.
- Лямбда-лічильник продовжує працювати й показує `Подій отримано: 3`.

**Крок 3. Обробка помилки.**

- Під час спроби повернути неіснуючу позичку виникає та перехоплюється виняток `InvalidOperationException`.
- У консолі виводиться повідомлення:

```text
[Очікувана помилка перехоплена]: Позичку з Id='UNKNOWN-ID' не знайдено.
```

- Лічильник залишається рівним `3`, оскільки подія не викликалася.

**Крок 4. Перевірка методу FindAll.**

- Виконується фільтрація активних позичок за допомогою лямбда-виразу:

```csharp
l => l.Status == LoanStatus.Active
```

- Метод повертає позички, статус яких відповідає `LoanStatus.Active`.

### 4.3. Перевірка запису в лог-файл

Виконати команду:

```powershell
Get-Content "logs/app.log"
```

**Очікуваний результат:**

- У файлі містяться рівно два рядки, які відповідають першій видачі та першому поверненню.
- Третя операція, виконана після відписки, не записується до файлу.
- Операція, що завершилася помилкою, також не створює запису про зміну стану.

Це демонструє роботу механізму відписки та підтверджує, що подія не викликається в разі невдалої операції.

### 4.4. Запуск із файловим сховищем

Для перевірки сумісності з лабораторною роботою № 5 виконати команду:

```powershell
dotnet run --project src/Cli -- --file
```

**Очікуваний результат:**

- У заголовку вказано сховище `FileLoanStore`.
- Підписники отримують події відповідно до виконаних операцій.
- Повідомлення, сформовані активним підписником, дописуються в кінець файлу `logs/app.log`.

### 4.5. Перевірка ізоляції доменного шару

Для перевірки відсутності прямих викликів консолі в коді `Core` виконати:

```powershell
Get-ChildItem "src/Core" -Recurse -Filter "*.cs" |
    Select-String -Pattern "Console\."
```

Для перевірки відсутності прямих посилань на лог-файл виконати:

```powershell
Get-ChildItem "src/Core" -Recurse -Filter "*.cs" |
    Select-String -Pattern "app\.log"
```

**Очікуваний результат:** обидві команди не знаходять збігів у файлах вихідного коду.

Це підтверджує, що доменний шар не залежить від конкретного способу виведення повідомлень і зберігання логів.

---

## 5. Висновок

Під час виконання лабораторної було опановано архітектурний патерн публікації-підписки (Observer) на основі механізму подій (event), стандартних делегатів (EventHandler<TEventArgs>, Func) та лямбда-виразів мови C#.
У результаті відокремлення бізнес-логіки від засобів сповіщення шар Core було позбавлено прямої залежності від System.Console та конкретної реалізації збереження логів. Це усунуло зв'язність компонентів, забезпечило повну свободу підключення нових споживачів (таких як Web API логер або Blazor UI на наступних тижнях) і спростило модульне тестування.
На практиці реалізовано безпечне підняття подій через умовний оператор Changed?.Invoke(...) виключно після успішної зміни стану системи, продемонстровано керування життєвим циклом підписників за допомогою операторів += і -=, а також використання механізму замикання (closure) над локальними змінними для збору статистики подій.
